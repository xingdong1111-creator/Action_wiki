1. 版本与结论

3.1 PaliGemma + action expert

π0 是 PaliGemma + action expert 的 flow matching VLA：

  • PaliGemma 2B：SigLIP So400m/14 视觉编码器 + Gemma 2B 语言模型
  • Action expert：Gemma 300M，单独一套权重，和 PaliGemma 同深度（18 层），宽度 1024
  • 输入三路图像：base_0_rgb、left_wrist_0_rgb、right_wrist_0_rgb，224×224
  • 动作：action_dim=32，action_horizon=50
llm = nnx_bridge.ToNNX(
    _gemma.Module(
        configs=[paligemma_config, action_expert_config],
        embed_dtype=config.dtype,
        adarms=config.pi05,
    )
)

gemma.Module 支持多个 expert，每个 expert 有自己的权重，token 按 expert 路由。

3.2 输入序列怎么拼

Prefix（图像 + 指令）：

3 张图 × 每张 256 token = 768 个 image token
prompt 最多 48 个 text token
prefix = 768 + 48 = 816 个 token

Suffix（状态 + 动作）：

π0:
  1 个 state token
  50 个 action token
  suffix = 1 + 50 = 51 个 token

π0.5:
  state 离散化后放进 prompt
  suffix = 50 个 action token

整体序列：

π0:   [prefix 816] + [suffix 51] = 867 个 token
π0.5: [prefix 968] + [suffix 50] = 1018 个 token

time 怎么进去：

  • π0：time embedding 不是单独 token，而是拼到每个 action token 的特征上：1024 + 1024 → MLP → 1024。
  • π0.5：time 通过 adaRMSNorm 注入 action expert，不拼到 token 上。

Attention 谁看谁：

Query能看
prefixprefix（full attention）
stateprefix + state
actionprefix + state + 所有 action

也就是说：prefix 不能看 suffix；state 不能看 action；action 能看 prefix、state 和所有 action。这是 block-level causal，block 内是 full attention。

make_attn_mask 就是在实现这个 block 边界：

attn_mask = cumsum[:, None, :] <= cumsum[:, :, None]
valid_mask = input_mask[:, None, :] * input_mask[:, :, None]
return jnp.logical_and(attn_mask, valid_mask)

3.2.1 不是 causal，是 block-causal

整个序列不是标准 causal mask。准确说是 block-causal：

Queryprefixstateaction
prefix✓✗✗
state✓✓✗
action✓✓✓
  • prefix 内部是双向 full attention：第 1 个 image token 能看最后一个 text token，反过来也能看。
  • prefix 看不到 suffix：prefix 的 query 只能看 prefix 的 key。
  • state 能看 prefix + state，不能看 action。
  • action 能看 prefix + state + 所有 action；action 之间也是双向 full attention，不是 token-level causal。

ar_mask 标记的是 block 边界，不是 token 级 causal：

prefix: 0 0 0 ... 0     -> block 0
state:  1               -> block 1
action: 1 0 0 ... 0     -> block 2

所以 cumsum 得到 block id 0/1/2，block[j] <= block[i] 就得到上面这张 block-lower-triangular 的 mask。

π0.5 少一个 state block：prefix 只能看 prefix，action 能看 prefix + 所有 action。

3.2.2 两个 expert 怎么实现

不是两个独立 LLM，而是一个 gemma.Module 里两套参数：

configs=[paligemma_config, action_expert_config]

每个 expert 的参数名用 _name(name, i) 区分：

expert 0（PaliGemma）: qkv_einsum, mlp, pre_attention_norm, final_norm
expert 1（Action）:    qkv_einsum_1, mlp_1, pre_attention_norm_1, final_norm_1

注意 expert 0 没有后缀，这样可以直接加载原来的 PaliGemma checkpoint；expert 1 才加 _1，从零初始化。

每层里：

  • prefix token 用 expert 0 的 QKV / FFN / 输出投影
  • suffix token 用 expert 1 的 QKV / FFN / 输出投影
  • 两边 QKV 按序列拼起来，做一次 joint attention
  • 输出按长度切回两个 expert

所以它是固定路由的 dual-expert Transformer：没有 gate、没有 top-k，路由由 token 段硬编码；attention 共享，FFN/QKV/输出投影不共享。

3.3 最后怎么出动作

18 层之后，suffix 的 51 个 token 变成 hidden states：

suffix_out: [B, 51, 1024]

只取最后 50 个 action token，丢掉 state token：

action_hidden = suffix_out[:, -50:]   # [B, 50, 1024]

过 action_out_proj：

v_t = action_out_proj(action_hidden)  # [B, 50, 32]

训练时：v_t 是速度场，和 u_t = noise - actions 做 MSE。

推理时：从噪声 x_1 开始，10 步 Euler：

x_t = x_t + dt * v_t

最后 x_0 就是 action chunk：[B, 50, 32]。

注意：50 个 action token 是并行解码的，不是逐 token 自回归；action_out_proj 是共享线性层，对每个位置独立应用。state token 不直接输出动作，它只通过 attention 影响 action token。

输出后还会过 output transforms：unnormalize、delta→absolute（如果配置了）、repack 回机器人接口。

3.3.1 推理时 10 步循环

推理不是把 2B 模型跑 10 次，而是：

阶段模型层数forward 次数层执行
PrefixPaliGemma 2B18118
去噪Action Expert 300M1810180
合计11198
  • Prefix 只跑一次，产出 18 层的 KV cache。
  • 每个去噪 step 只跑 Action Expert，读 prefix KV cache。
  • 每个 step 的输入是当前的 x_t 和 t，输出 v_t。
  • Euler 更新：x_t = x_t + dt * v_t，t 从 1.0 走到 0.0。
  • 10 个 step 后得到 x_0: [B, 50, 32]。
  • 不是 PaliGemma 2B 跑 10 次；PaliGemma 只跑 1 次，Action Expert 跑 10 次。

3.4 Flow matching loss

compute_loss（pi0.py:189）：

\[ x_t = t \cdot \epsilon + (1-t) \cdot a,\quad u_t = \epsilon - a \]
\[ \mathcal{L} = \| v_\theta(x_t,t) - u_t \|^2 \]
x_t = time_expanded * noise + (1 - time_expanded) * actions
u_t = noise - actions
v_t = self.action_out_proj(suffix_out[:, -self.action_horizon :])
return jnp.mean(jnp.square(v_t - u_t), axis=-1)

t 采样是 Beta(1.5, 1) * 0.999 + 0.001。

3.4.1 训练时的两个随机变量

每个训练 step 采样三样东西：

  • 数据样本：actions / images / prompt / state
  • noise：每个 step 重新采样
  • t：每个 step 重新采样

固定一个数据样本时，就是两个随机变量：noise 和 t。

变量控制什么
noisev_true = noise - actions，决定路径和目标速度
tx_t = t*noise + (1-t)*actions，决定路径上的哪个点

所以：

  • 同一个 (actions, noise)：v_true 恒定，t 只改变 x_t
  • 不同 noise：v_true 不同，路径不同
  • 模型学的是 v(x_t,t) 条件平均速度，不是背单条路径的常数

一维例子：actions=1.0，noise=-1.0，则 v_true=-2；t=0.25 时 x_t=0.5，t=0.75 时 x_t=-0.5，两个点的目标速度都是 -2。

训练推理
noise每个 step 重新采样只在开始采样一次
t每个 step 随机采样固定 1 -> 0，10 步
x_t由 actions/noise/t 构造由上一步 Euler 更新

3.4 Sampling

sample_actions（pi0.py:217）：

  • 先跑 prefix，填 KV cache
  • 从 t=1 到 t=0，默认 10 步
  • 每步 x_t += dt * v_t
  • 注意代码里 t=1 是噪声、t=0 是目标，和论文相反，注释里也写了

3.5 为什么这样设计（小技巧）

设计原因
PaliGemma 2048保留预训练视觉语言模型的结构和能力
Action Expert 1024 / 300M动作生成任务比视觉语言理解窄，300M 够用，省算力
共享 attention不需要额外的 cross-attention，action expert 直接读 prefix
QKV 都投到 8×256两个 expert 宽度不同，但 head 空间一致，才能拼成一条序列
输出投影回各自宽度prefix 回 2048，action expert 回 1024
固定路由prefix/suffix 天然分开，不需要 learned gate 和 load balancing
block-causal maskprefix 双向、action 看 prefix、prefix 不看 action，符合 flow matching
prefix KV cache2B 只跑 1 次，300M 跑 10 次，推理成本可控

代价：

  • 两个 expert 的 head 几何必须一致（8×256），限制了 action expert 的配置。
  • 固定路由不如 learned MoE 灵活。
  • 10 步去噪仍然有延迟。

一句话：大模型理解 + 小模型生成 + 共享 attention + KV cache，目标是效果接近大模型，推理成本接近小模型。

4. π0-FAST

核心文件：

src/openpi/models/pi0_fast.py:134   class Pi0FAST

π0-FAST 是 自回归 VLA，没有 action expert：

  • 用 FAST action tokenizer 把 action chunk 变成离散 token
  • 直接走 PaliGemma 2B，做 next-token prediction
  • action_horizon=32，max_token_len=250
  • loss 是 token-level cross entropy，带 token_loss_mask
  • 推理是 KV-cache 自回归解码，最多 256 步，遇到 EOS 停
targets = jax.nn.one_hot(observation.tokenized_prompt[:, 1:], vocab_size)
pre_logits = self.PaliGemma.llm(embedded_prefix=input_token_embeddings[:, :-1], ...)
logits = self.PaliGemma.llm(pre_logits=pre_logits[:, -targets.shape[1]:])
logp = jax.nn.log_softmax(logits, axis=-1)
loss = -jnp.sum(targets * logp * loss_mask, axis=-1) / loss_mask.sum(-1)

5. π0.5：和 π0 的差异

Pi0Config(pi05=True)。

5.1 state 进 prompt，不进 suffix

π0：state 是一个 continuous token，放在 suffix 里。

π0.5：state 先离散化，再拼进语言 prompt：

Task: {prompt}, State: {state_str};
Action:

state 被分到 256 个 bin（范围 [-1, 1]），每个值变成一个数字 token。所以 π0.5 的 suffix 只有 50 个 action token，没有 state token。

配置项是 discrete_state_input=True，默认跟随 pi05=True。

5.2 time 用 adaRMSNorm，不拼到 token 上

π0：time embedding 复制 50 份，和每个 action token 拼起来，再过 MLP。

π0.5：time embedding 过 time_mlp_in/out（两层 Linear + swish），得到 adarms_cond: [B, 1024]，传给 action expert 的 RMSNorm：

use_adarms=[False, True]

也就是 PaliGemma expert 用普通 RMSNorm，action expert 用 adaRMS。adaRMS 的做法是：

modulation = Dense(3 * width)(cond)
scale, shift, gate = split(modulation, 3)

normed = x / sqrt(mean(x^2) + eps)
normed = normed * (1 + scale) + shift

residual = x + y * gate

RMSNorm 的位置：每个 Transformer block 里有两个 pre-norm：attention 前和 FFN 前；18 层共 36 次；最后还有一个 final_norm，所以每个 expert 一共 37 次。π0.5 的 action expert 这 37 次都是 adaRMS；PaliGemma 的 37 次是普通 RMSNorm。

time 不是只加在输入上，而是注入 action expert 每一层的 pre_attention_norm_1 和 pre_ffw_norm_1，所以每一层都能感知当前 flow matching 的 t。

5.3 序列长度

prefix = 768 image token + 200 prompt token = 968
suffix = 50 action token
total  = 1018

max_token_len=200，比 π0 的 48 长很多，因为 state 也进了 prompt。

5.4 只支持 flow matching head

openpi 里的 π0.5 只支持 flow matching，不支持 π0-FAST 的 autoregressive head。

5.5 配置差异

配置action_horizonstate 输入
pi05_aloha50离散进 prompt
pi05_droid15离散进 prompt
pi05_libero10discrete_state_input=False，state 被忽略
pi05_full_droid_finetune16离散进 prompt
pi05_droid_finetune16离散进 prompt

π0.5 的其他结构（18 层、双 expert、共享 attention、10 步采样）和 π0 一样。

5.6 训练/推理：和 π0 基本一样

  • compute_loss 和 sample_actions 的结构不变，只是 suffix 没有 state token，adarms_cond 传给 llm。
  • 训练时一次 joint forward；推理时 prefix KV cache 一次，Action Expert 10 步。
  • π0.5 的 50 个 action token 仍然是并行解码，flow matching head 不变。

6. π0.6 / π0.7：论文有，代码没有

截至 2026-11-12，官方 openpi 没有 π0.6 / π0.7 的代码和权重。

模型发布架构关键创新代码/权重
π0.6 / π*0.6 2025-11-17 Gemma3 4B + 860M action expert，约 5B Knowledge Insulation；最多 4 图 448×448；flow matching + FAST token；5 步去噪；RECAP（π*0.6） 未开源
π0.7 2026-04-16 5B；Gemma3 4B + MEM video history encoder + 860M action expert MEM 视频记忆；多模态上下文（语言/metadata/subgoal image）；高层策略 + 低层 VLA；BAGEL world model；5 步；组合泛化 未开源，Pi API beta

6.1 π0.6 的新东西

  • 更大的 backbone：Gemma3 4B VLM + 860M action expert，总共约 5B。
  • 更高分辨率/更多相机：最多 4 张图，448×448（base + 两个 wrist + 可选 backward）。
  • Knowledge Insulation：VLM 预测 FAST token + co-training 数据；action expert 预测连续 flow matching；action 梯度不回传 VLM。
  • 双路输出：模型可以同时产生 flow matching 连续动作和 tokenized discrete 动作；执行主要用连续动作。
  • heterogeneous prompt：prompt 可以带执行质量、策略等 conditioning metadata。
  • 5 步去噪：H100 上 3 路相机约 63ms 出一个 action chunk。
  • RECAP（π*0.6）：advantage-conditioned RL，用 demonstration + 人工纠正 + 自主经验；官方说 throughput 翻倍、failure rate 减半。

6.2 π0.7 的新东西

  • MEM 视频记忆：MEM-style video history encoder，对历史帧做时空压缩，输出固定数量 token；不再只看当前帧。
  • 多模态上下文：语言、episode metadata（质量/策略）、控制模态、subgoal images。
  • 高层 + 低层：高层 semantic policy 出子任务，低层 VLA 出动作。
  • 世界模型：BAGEL 14B 生成 subgoal images，作为视觉目标条件。
  • 异步推理：subgoal / 子任务生成和 VLA 推理分开线程，VLA 用最新上下文。
  • Steerable：通过 metadata、subgoal、控制模式控制“怎么做”，不只是“做什么”。
  • 组合泛化：官方展示 zero-shot cross-embodiment、新任务组合、未见过的 laundry folding。
  • 5 步去噪：5B 模型，5 步 flow matching。

9. PyTorch 版

src/openpi/models_pytorch/pi0_pytorch.py:84   class PI0Pytorch

PyTorch 版是 π0 / π0.5 的移植，用 HuggingFace 的 PaliGemma + Gemma expert。几个关键点：

  • 需要打 transformers_replace patch（AdaRMS、精度控制、KV cache）
  • 支持 gradient checkpointing
  • 支持 torch.compile
  • 不支持 π0-FAST
  • 不支持 混合精度训练、FSDP、LoRA、EMA
